## In 60 seconds

I wanted a portfolio piece that took a different approach from my other work, on a small, familiar problem: a site on the icanhazdadjoke API with search, a random joke, a page per joke with a copy button, a header and footer, and a tidy layout. I built that as **The Dad-a-base**, a dad-joke paper styled as a newspaper's Sunday funnies, and then took it further: Favorites, Share, keyboard shortcuts, a design system, an Error state for every way the API can fail, and a press-and-hold Groan button with its own leaderboard.

- **Stack:** Vue 3 with `<script setup>` and TypeScript, Vite, vue-router and Pinia. All API data goes through Apollo Client, talking to the REST API through `apollo-link-rest`, with Zod checking every response.
- **Quality:** every route runs end to end on three browsers, with axe in both themes and reflow at 320px. Unit and component tests cover over 95% of statements, against a 90% gate.
- **Process:** nine milestones, then five follow-ups (a mobile pass, a phone menu, the Groan button, a refactor and faster CI), each with a GitHub issue, a pull request and a journal entry with screenshots. From the app shell on, each that changed what a screen reader meets also had a VoiceOver pass that I ran on a Mac and an iPhone.

The boxes marked **Live** on this page are the app's own components, given fixed props, not screenshots of them.

## Engineering

### The stack, and why

Vue 3, TypeScript and Vite, with plain CSS. How the components are laid out is part of what I wanted this piece to show, so I wrote the layout myself rather than reaching for a component library. Nuxt would have brought server rendering this app doesn't need, and hidden the routing and data wiring I wanted to show. Tailwind's utility classes can't express the semantic and domain tokens the design system is built on.

### Apollo over REST

I wanted this piece to show a different data layer from the rest of my portfolio, Apollo and GraphQL, but icanhazdadjoke's own GraphQL endpoint can't build this app. Its schema has one field, which returns one random match for a search, so there's no search list and no pagination. The REST API has everything. So every request is a GraphQL document with an `@rest` directive, which `apollo-link-rest` turns into a REST call. There's no GraphQL server to run.

- **Zod is the single source of truth for types.** With no schema, there's nothing for a code generator to read, so each response is parsed by a Zod schema at runtime, and the static types come from the same schemas.
- **Each Joke is stored once,** as `Joke:id`, whether it came from Search, Random or Favorites. Opening a Joke you've already seen makes no request, and tests check that.
- **I chose Apollo 3, not Apollo 4's prereleases.** Version 4 would have needed a release candidate of `apollo-link-rest` and a beta of `@vue/apollo-composable`, which is too much risk with a deadline.

### Three homes for state

Every piece of state lives in exactly one place, chosen by one question each:

- **Can someone link to it? Then it's in the URL:** the search term and page, a Joke's id, and the Favorites filter. Reload, Back and sharing all just work.
- **Did the API say it? Then it's in Apollo's cache:** Jokes and pages of search results, normalised so one Joke is one entry.
- **Did the visitor choose it? Then it's in Pinia:** Favorites, Groans, recent searches, the theme, the shortcuts switch and toasts. What should outlive a visit is saved in this browser, and nowhere else, through one helper, `useStoredRef`: it checks what it reads back with Zod, so bad data falls back rather than breaking the page, and keeps open tabs in step.

### A design system built from tokens

Styles use custom properties in three layers. **Primitives** are the raw palette and scales. **Semantic** tokens say what a value is for. **Domain** tokens are the Dad-a-base's own parts. Components may only use the last two, and dark mode only changes the semantic layer.

Tests enforce the rules: semantic tokens only reference primitives, domain tokens only semantic ones, no component touches a primitive, and every text and border pairing meets WCAG AA in both themes. Stylelint bans raw `px` and colour values outside the token files. The `/design-system` page reads the tokens from the same stylesheets, so its documentation can't drift from the code.

One bug taught me how custom properties really work. A `var()` resolves where the property is declared, not where it's used, so domain tokens declared only on `:root` stayed light inside a dark panel. axe caught the contrast failure, and domain tokens are now declared again on every themed element.

### The testing approach

- **Vitest** covers the logic and the views: stores, schemas, cache policies, the Pagination window, the error mapping, composables, and each page rendered as the visitor sees it.
- **Storybook** has stories for every component, each with a play test run in Chromium, and axe failing a story on any violation.
- **Playwright** runs every route end to end on desktop Chromium, mobile WebKit and mobile Chrome, with axe in both themes and reflow at 320px. The checks that don't depend on the browser run once, and each browser is its own CI job, so CI takes about three and a half minutes, down from nine.
- **MSW** answers the API in all three, from one set of handlers. One smoke test calls the real API, in its own CI job that can't block a merge, because the API isn't mine.

The tests earned their keep. They caught a cache write that silently stored empty Jokes, a WebKit race in how tests saved data before loading a page, axe measuring contrast while a page was still fading in, a Storybook story that passed alone but failed after another story left data behind, a hidden tooltip that made a phone scroll sideways, and a button whose name didn't match its label.

### Building with Claude

I built this with Claude Code, Anthropic's coding agent, and I'd rather show how than hide it.

- **I wrote the plan first.** The spec, the domain glossary, the voice guide and the architecture decision records came before the code, and a `CLAUDE.md` file holds the project's rules, such as "Zod schemas are the single source of truth" and "ask before pushing".
- **Claude built each milestone to the spec,** with its tests, and recorded every decision it made by default in the journal, under "Defaults, not asked", so I could see which choices were mine.
- **I reviewed each milestone running,** locally or on a preview deploy, and asked for changes. Milestone 5 alone took more than a dozen changes: the Remove button pinned over the card, the broken-heart icon, the falling animation, search and pages on Favorites, and a heart on every Favorite.
- **Some of my requests had accessibility catches, and Claude flagged them** with the accessible version. "Faved" meant dropping the toggle-button role. A centred tooltip would have run off a phone's screen, so it stays right-aligned there. A disabled button needed to keep its focus.
- **Bigger features started with a grilling.** Before any code for the Groan button, Claude asked me its design one round of questions at a time, each with a recommended answer, until nothing was left assumed: whose leaderboard it is, how a hold becomes a score, what a keyboard does, what happens on a scroll.
- **I tested on my own phone.** Claude deployed previews I could open on an iPhone. The first Groan button there was clunky: a tap started a hold that only a second tap ended. The fix, a long press only and a lift heard anywhere on the page, came from that, since no test can drive a real finger.
- **Once it was done, I asked what to change.** Claude reviewed the architecture and found what Groans had copied from Favorites, which became a refactor with no change in behaviour. I asked whether we were testing too much: not too much, it said, but some checks ran on three browsers for nothing, and the browsers ran one after another. CI went from nine minutes to three and a half without dropping a check.
- **I kept the outward-facing steps.** Claude asked before every push, issue and pull request, and I ran every VoiceOver pass myself.

Owning it also meant leaving things out. Early prototypes showed a "groan rating" on every Joke, but the API has none, and inventing one would put made-up numbers on real content, so I left it out. Later I brought the idea back the honest way: the only score is your own Groan, below.

### Designing the flows

**Search** runs as you type, and the address follows: the term is `?q` and the page is `?page`. Typing replaces the history entry rather than adding one, so Back skips your keystrokes, while turning a page adds one, so Back returns to the page before. A recent search is remembered when you press Enter, turn a page or open a Joke, not on every pause, which would save "c", "ca" and "cat". A bad or out-of-range `?page` is quietly replaced with the nearest real one.

The Pagination window keeps 11 numbers in view and stays full at both ends, so the controls never shift under your pointer as you page through.

<PaginationStates />

**When the API fails,** the page becomes a correction notice, in place: the address doesn't change, and "Try again" really tries again. Each code has its own notice, with a pun in the headline and a plain explanation under it. Being rate-limited (429) isn't the same as the server being down, so it says so. The API reports some errors with HTTP 200 and the real status in the body, so the client reads the body before it trusts the status.

<ErrorStates />

**On a phone,** the sections move into a drawer from the left, behind a hamburger at the top left. It's a native modal dialog, so focus stays inside and the page behind is inert, and choosing a section, Close, Escape or a tap beside it closes it, with focus back where it was.

**Favorites** are kept as whole Jokes in the browser, so the Favorites page needs no API calls. They're written into Apollo's cache too, so opening one is instant. They can be searched and paged like Search. Removing one plays a short "falls off the fridge" animation and moves focus to the next Joke's button, so a keyboard user doesn't lose their place.

### A moment of delight

The last feature is there for fun. The **Groan button** lets you say how bad a Joke is the way you would at the table: press and hold, and the longer you groan, the worse it was. It fills from sunshine to hot pink over three seconds while its "Ugh" gains an h every quarter second, shakes when it's full, and lets go with a comic "GROAN! 7.2" burst. Every Groan goes on a **Groan Leaderboard**, worst first.

<LiveFigure caption="GroanButton, given a Joke as a prop. Press and hold it: the Groan is real, and goes on your Groan Leaderboard.">
  <GroanButton
    joke={{
      id: 'daaUfibh',
      joke: 'Why was the big cat disqualified from the race? Because it was a cheetah.',
    }}
  />
</LiveFigure>

- **It reverses an earlier call, and says so.** I'd left ratings out because the API has none. A Groan isn't a rating made up for the Joke: it's your own reaction, saved in your browser. So the board is yours alone. A shared one, with no accounts behind it, would be a leaderboard of whoever held longest.
- **A hold has to work without a mouse.** Space and Enter hold it as a pointer does, a held key's repeats are ignored, and Escape cancels. On a phone, only a long press groans: a tap shows how it works instead, and a scroll that takes over cancels it.
- **The name follows the label.** axe caught the first version, where the name stayed "Groan" while the button read "Ughhh" (WCAG 2.5.3, Label in Name). Now it's "Groan: Ughhh", so the words you see are in the name, and speech input can still say "Groan".
- **The button grows with its "Ughhh", but never moves.** It keeps room for its widest label beside the other buttons, and wraps to its own line only when that room isn't there. It holds on to the pointer while it's held, and only sliding more than a touch target away cancels.
- **The gradient was chosen by the numbers.** The label stays the text colour over all of it, and a test checks it at 4.5:1 against every point along the gradient, in both themes.
- **Motion is optional here too.** Under reduced motion there's no nudge on hover, no shake and no flying burst, but the fill and the "Ughhh" still show the hold.

### Look, voice and accessibility

The look came from four rounds of throwaway prototypes: a retro terminal, a 70s den and a comic zine first, then calmer versions of the zine, then mastheads, then headline fonts. I chose the **Sunday funnies**: a blackletter masthead with a dad peeking over his newspaper as its crest, Oswald headlines, newsprint colours, and each Joke in a halftone comic frame.

The voice has rules, written down so they hold: the joke goes in the headline, and plain words go underneath. Controls are never puns: the theme toggle is "Dark theme", not "Night edition". There are no exclamation marks outside the Jokes themselves.

Accessibility is built in rather than checked at the end, and the details changed the design more than once:

- **Focus follows navigation** to each new page's headline, as a page load would, and a skip link is the first stop on every page.
- **The Fave button reads "Faved" once a Joke is saved,** so it isn't also a toggle button: a toggle's name must stay the same in both states, or a screen reader announces the state twice.
- **Busy buttons keep their focus.** "Another" ignores presses while it loads instead of using the `disabled` attribute, which would throw a keyboard user back to the top of the page every time.
- **The single-key shortcuts can be turned off** (WCAG 2.1.4), because speech input can press them by accident.
- **Tooltips can be dismissed** with Escape and stay while the pointer is over them (WCAG 1.4.13).
- **Motion is optional.** Every animation stops under reduced motion.

## What I rejected

- **The upstream GraphQL endpoint.** It has no search list and no pagination, so it can't do what the site needs.
- **A backend for the frontend.** A small GraphQL server could have bridged the REST API into a proper paginated schema and shown schema design, but it would have added a server, its deploys and its tests, for a gain a visitor would never notice.
- **A shared Groan Leaderboard.** The whole internet's worst jokes would be fun, but with no accounts it would rank whoever held longest, or scripted the longest hold, and it would need a backend to run and police. So the Visitor's data stays in their browser, a decision with its own architecture decision record.
- **Infinite scroll.** Pages you can link to, Back that works, a footer you can reach, and a screen reader that knows where it is all matter more than saving a click.
- **Component libraries.** How I lay out components is part of what this piece shows, so a library would have answered the question for me.
- **Apollo 4's prereleases.** They're current, but a release candidate and a beta are a risk I didn't need to take with a deadline.
- **A "reveal the punchline" interaction.** The comic-zine prototype split each Joke into a setup panel and a punchline panel, and I planned it for the end. I dropped it: it adds an interaction to learn and code to maintain, and many Jokes have no natural break, so any rule for finding one would guess wrong.
